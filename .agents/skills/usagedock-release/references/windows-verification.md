# 通常のWindows環境で更新を確認する

## 更新前の観測

Computer Useの返すアプリとウィンドウからUsageDockを一意に選ぶ。スクリーンショット、実行パス、設定 → アプリ情報の番号を確認する。テストが必要な旧版を先に手動更新してしまわない。

通常の既存インストール先は `%LOCALAPPDATA%/UsageDock/UsageDock.exe`。ユーザーが別の場所へ入れている場合は観測結果を優先する。

以下は別コピーの疑いがある。

- 実行パスに `Packages/OpenAI.Codex_*/LocalCache` が含まれる。
- シェルのファイル情報と画面の番号が違う。
- シェルからのセットアップだけが「最新版がインストール済み」と判断する。

シェルのパス表示自体も仮想化される場合があるため、文字列のファイルパスだけで同じ実体と判断しない。過去の観測はルートの `docs/update-verification-0.4.4.md` にある。初期の更新失敗がどの内部段階で起きたかは確定していない。

## 通常の更新経路を先に試す

1. 公開後、更新前から動いていた通常環境のアプリで「更新を確認」を押す。公開番号が出ることを確認する。
2. 既存の依頼・許可の範囲で「更新して再起動」を実行する。待機・エラー・インストーラーの状態を観測する。画面が消えただけで成功にしない。
3. 再起動したアプリを一覧から選び直す。通常環境の実行パス、設定画面の新番号、更新確認での最新版判定を確認する。
4. 変更した機能を実画面で確認する。常駐UIなら、リングへのカーソル移動、詳細への移動、外への移動、クリック固定、Escapeなど変更に関係する操作を選ぶ。短い静止画だけから全てのちらつきが解消したと断定しない。
5. 既存の接続と設定が維持されていることを確認する。アカウント解除を検証の都合で強制しない。

「更新を検出できる」「最新と判定される」だけでは、ダウンロード・インストール・再起動を通した確認にはならない。初めから最新版だった場合、検証のためだけにダウングレードや中身のない新リリースを作らず、未検証の経路を明記する。

## 失敗した場合

- エラーの文言と段階を記録する。診断に対応した版では画面に示される `updater.log` の場所を調べる。シェル側と通常環境側のログを混同しない。
- 一時的な通信失敗なら状態を再観測して一度再試行する。同じ失敗が続いたら操作を連打せず原因調査へ移る。
- 署名不一致なら公開先・鍵・成果物を照合する。署名検証、OSの保護、権限の確認を無効にしない。
- 旧版の不具合で更新できないときは、公開先と同一ハッシュの署名付きセットアップで復旧できる。ただし手動復旧の成功をアプリ内更新の成功と報告しない。
- 新しいコード修正が必要なら通常の修正・新番号の公開手順へ戻る。既存の公開済み成果物を上書きしない。

## 仮想化を避けてセットアップで復旧する

1. Computer Useで通常のエクスプローラーを開く。アドレス欄へ配布フォルダーのパスを入力する。シェルコマンドは入力しない。
2. ファイル一覧の公開版セットアップを実際に開く。シェルの `Start-Process` や直接の `launch_app` だけでは通常環境でのインストールを保証できない。
3. 観測した既存のインストール先へ更新する。旧版を先に消す必要がない上書き更新では「Do not uninstall」を選び、設定・認証を保持する。不要なショートカットを追加しない。
4. 更新に伴うUsageDock終了と起動を進める。認証やOS保護の画面など、操作できない画面が出たら、その操作だけユーザーへ引き継ぎ、独立した検証は進める。
5. 完了画面から起動したプロセスの実行パスと、画面の番号を再観測する。必要なら通常の既存ショートカットからの起動も確認する。

## Computer Useでの観測の注意

- 利用中のスキル・ツールのAPIを読んで使用する。古いウィンドウIDや要素番号を次の画面で使い回さない。
- 本環境ではクリック直後にアクセシビリティのツリーが古いまま、画像だけが新しいことがあった。次の操作は更新後の状態を観測して決める。
- `coordinate input geometry is unavailable` が出たら最新のスクリーンショット付き状態を取り直す。新しい観測から一度再試行し、同じ失敗を連打しない。
- モーダルの要素が見つからない場合はウィンドウ一覧と画像を取り直して操作先を特定する。通常画面のボタンを推測して押さない。
