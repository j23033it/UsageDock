# UsageDockの変更から実機更新まで

このスキルは配置されたCodexBarリポジトリ専用。グローバルな設定や他のアプリへ適用しない。リポジトリルートはこのフォルダーの3階層上。

## 最初に確認すること

1. ルートの `AGENTS.md` を読み、現在の依頼範囲と許可を確認する。既存の公開許可を引き継ぐ。スキル自体を新しい公開先・ソースコード送信・アカウント削除への許可と解釈しない。
2. `git status`、現在のブランチ、変更対象を確認する。既存機能の修正は現在のブランチ、新機能はプロジェクトのブランチ規約に従う。
3. 通常のWindows環境で動くUsageDockの更新前バージョン・実行パスをComputer Useで観測する。変更する挙動と更新後の確認項目を短く記録する。実機が使えなければ開発と配布準備を進め、実機確認を未確認のまま区別する。

## 進め方

- 実装では既存の `src/` と `src-tauri/src/` を編集する。`dist/`、`release/`、`target/` を編集元にしない。変更した挙動に合うテストを行い、小さくコミットする。
- アプリ変更の通常の完了範囲は、実装・必要な検証・新しい番号での公開・通常環境でのアプリ更新・変更箇所の実画面確認。ユーザーがローカル検証や公開のみを指定した場合はその範囲に従う。
- 配布段階では [公開手順](references/release.md) を読む。既存の `scripts/release.ps1` を使い、署名鍵やビルド手順を作り直さない。公開先は `j23033it/UsageDock-Releases`。ソースコードはローカル管理を保つ。
- 更新操作の前には [Windows実機確認](references/windows-verification.md) を読み、利用可能な `computer-use` スキルのAPIと操作規則を読み込む。
- 更新失敗の依頼なら、先に実機のエラーを観測し、失敗した段階を特定する。復旧だけで足りる場合は、不要なコード変更や新バージョンを作らない。

## 毎回守る境界

- シェルで見えたEXEの番号・ハッシュだけで実機更新を完了としない。Codexのパッケージ専用領域に別コピーができることがある。
- 単体EXEを渡して完了にしない。同じ公開バージョンのファイルを別内容へ差し替えない。
- 実機の更新前後で別の保存領域へ切り替わっていたら、通常環境の確認をやり直す。仮想化は過去に確認した原因の一つであり、全ての更新失敗の原因と決めつけない。
- 公開ファイル検証、更新の検出、アプリ内ダウンロード・インストール・再起動、変更機能の確認は別々に判定する。「最新版です」はインストール経路の成功証明ではない。
- 実アカウントの接続解除・再認証を確認のためだけに行わない。自動テストや許可済みの検証用接続で確認し、実アカウントは保持する。
- 文書・スキルだけの変更なら、その検証とローカルコミットまで。アプリの番号変更、公開、インストールは不要。

## 完了の記録

ルートの `docs/update-verification-<公開バージョン>.md` に、変更コミット、テスト結果、公開URL、成果物照合、更新前後の画面上の番号と実行パス、更新経路、機能の確認結果、未確認項目を簡潔に残す。アカウント名や秘密値は書かない。

手動セットアップで復旧した場合はその経路を明記し、アプリ内更新を検証済みとしない。失敗・権限不足・ユーザー操作待ちは対象と理由を具体的に報告する。最後に `AGENTS.md` のGit後片付けと状態確認を行う。
